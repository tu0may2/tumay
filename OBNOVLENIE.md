# Git и обновление терминала на сервере

Два разных вопроса, которые часто путают:

* **Git** хранит историю кода: что менялось, когда и зачем. Он живёт на
  GitHub и на вашем компьютере, к работающему серверу отношения не имеет.
* **Обновление сервера** — это перенос новой версии кода на машину в облаке
  и перезапуск службы. Git тут удобен как средство доставки, но не обязателен.

Ниже — сначала практика (как накатить обновление), потом git как таковой.

---

## Часть 1. Как накатить обновление на сервер

### Способ А. Через git — рекомендую

Один раз настраивается, дальше обновление занимает две команды.

**Первоначальная настройка (один раз).** Подключитесь по SSH и выполните:

```
sudo apt-get update
sudo apt-get install -y git rsync
sudo git clone https://github.com/tu0may2/tumay.git /opt/treasury/src
```

Клон делаем от root — это просто папка с исходным кодом, из которой файлы
потом копируются в рабочие места; сама она не запускается и правами
пользователя `treasury` владеть не обязана.

Дальше связываем клон с рабочей папкой. Терминал ожидает, что `backend` и
`frontend` лежат рядом, поэтому переносим оба:

```
sudo rsync -a --delete \
  --exclude 'treasury.db*' --exclude '.env' --exclude '.venv' --exclude '__pycache__' \
  /opt/treasury/src/backend/ /opt/treasury/backend/
sudo rsync -a --delete /opt/treasury/src/frontend/ /opt/treasury/frontend/
sudo chown -R treasury:treasury /opt/treasury/backend
```

**Каждое следующее обновление — эти три команды:**

```
sudo git -C /opt/treasury/src pull
sudo bash /opt/treasury/src/backend/deploy/setup.sh /opt/treasury/src/backend
sudo rsync -a --delete /opt/treasury/src/frontend/ /opt/treasury/frontend/
```

Скрипт `setup.sh` идемпотентен: он обновит код и зависимости, но **не тронет**
базу `treasury.db` и файл `.env` с паролем — они исключены явно. После этого
служба перезапускается сама.

Проверка, что всё поднялось:

```
sudo systemctl status treasury
```

Строка `active (running)` — готово. Если нет, смотрите журнал:

```
sudo journalctl -u treasury -n 50 --no-pager
```

### Способ Б. Через WinSCP, без git

Если возиться с git не хочется: перетащите папки `backend` и `frontend` из
нового архива в `/home/<ваш-пользователь>/`, затем на сервере:

```
sudo bash /home/<ваш-пользователь>/backend/deploy/setup.sh /home/<ваш-пользователь>/backend
sudo rsync -a --delete /home/<ваш-пользователь>/frontend/ /opt/treasury/frontend/
sudo systemctl restart treasury
```

Работает так же, просто копирование ручное.

### Если обновление сломало терминал

Откат к предыдущей версии — одна команда, если настроен способ А:

```
sudo git -C /opt/treasury/src checkout HEAD~1
sudo bash /opt/treasury/src/backend/deploy/setup.sh /opt/treasury/src/backend
```

`HEAD~1` — «на один коммит назад». База при этом не трогается.

### Перед обновлением: копия базы

Занимает секунду и снимает главный риск — потерю портфеля и сделок:

```
sudo cp /opt/treasury/backend/treasury.db ~/treasury-$(date +%F).db
```

Скачать копию себе можно через WinSCP.

## Часть 2. Git: что это и зачем

### Идея

Git хранит **снимки** состояния кода. Каждый снимок — коммит — помнит, что
именно изменилось, когда и с каким пояснением. Из этого следует главное:
любое изменение можно посмотреть, отменить или сравнить с любым другим.

Два места, где живёт код:

* **репозиторий на GitHub** — общая копия, к ней обращается сервер;
* **рабочая копия** — папка на вашем компьютере или на сервере.

### Команды, которые нужны в работе

```
git status              # что изменилось прямо сейчас
git log --oneline -10   # последние 10 коммитов: что и когда меняли
git pull                # забрать свежую версию с GitHub
git diff                # посмотреть текст изменений построчно
```

Если правите код сами:

```
git add .                          # отметить изменения к сохранению
git commit -m "Что и зачем менял"  # сохранить снимок
git push                           # отправить на GitHub
```

Сообщение коммита пишите так, чтобы через полгода было понятно **зачем**
менялось, а не что: «Починил НКД по флоатерам» полезнее, чем «правки».

### Ветки

Ветка — параллельная линия правок. Смысл: чинить или добавлять что-то, не
трогая работающую версию.

```
git branch                    # какие есть ветки, где вы сейчас
git checkout -b novaya-vetka  # создать новую и перейти в неё
git checkout main             # вернуться к основной
```

Рабочий порядок: правки делаются в отдельной ветке, проверяются, и только
потом сливаются в `main`. На сервер разворачивается `main` — так на боевой
машине не окажется недоделанного.

### Как посмотреть историю не в консоли

На GitHub: вкладка **Commits** в репозитории. Там вся история с пояснениями,
по клику — построчные изменения: зелёным добавленное, красным удалённое.

### Чего git не делает

* Не хранит базу данных — `treasury.db` намеренно исключён (`.gitignore`).
  Портфель и сделки живут только на сервере, их бережёт копия из части 1.
* Не хранит пароли — `.env` тоже исключён.
* Не обновляет сервер сам. Обновление запускаете вы командами из части 1.

## Часть 3. Автообновление при каждом изменении кода

Если захотите, чтобы сервер обновлялся сам после отправки кода на GitHub —
это делается через GitHub Actions. Понадобится:

1. Создать SSH-ключ для деплоя и положить приватную часть в секреты
   репозитория (Settings → Secrets and variables → Actions).
2. Добавить в репозиторий файл `.github/workflows/deploy.yml`, который при
   push в `main` подключается к серверу и выполняет команды обновления.

Стоит делать, когда обновления станут частыми. Пока их несколько в месяц,
три команды из части 1 быстрее и понятнее — и, что важнее, вы видите
результат сразу и можете откатиться, а не узнаёте о поломке от пользователей.
